Troubleshooting

Common operational problems with symptoms, likely causes, and safe fixes.

Patent module produces no output

SymptomNo patent alerts. Logs may say provider is disabled.
Likely causePatent provider is disabled by default. The old PatentsView endpoint (search.patentsview.org) was decommissioned in 2026.
How to checkpython -c "from modules.patent_sentinel import check_patent_provider_health; import asyncio; print(asyncio.run(check_patent_provider_health()))"
Safe fixThis is expected behavior. The pipeline runs normally without patent collection. To re-enable the legacy path: PATENT_PROVIDER=legacy_patentsview (only if you have a confirmed working endpoint). The USPTO ODP adapter is planned for a future packet.

Targeted mode runs nothing / missing targets

Symptomlighthouse --module targeted runs but collects nothing. lighthouse targets shows empty or unexpected profiles.
Likely causedata/targets.json does not exist, is invalid, or all profiles are disabled.
How to checklighthouse targets — validates and shows routing plan. cat data/targets.json to inspect the file.
Safe fixIf missing, copy the seed: cp seed/targets.json data/targets.json. Validate: lighthouse targets --show-routes. Check that at least one profile has "enabled": true and the signals you want.

Start9 data wiped after reinstall

SymptomAfter updating or reinstalling the Start9 package, all historical data is gone. lighthouse correlations returns nothing.
Likely causeStartOS performed a volume reset on uninstall. A same-version reinstall (stop → uninstall → install → start) wipes /data.
How to checkpodman exec lighthouse.embassy env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db lighthouse status
Safe fixIf you had a StartOS backup, restore it: Lighthouse → Actions → Restore Backup. If no backup exists, the data is lost. Going forward: always create a StartOS backup before any package update. Use Update (not uninstall + reinstall).

Graph queries return empty results

Symptomlighthouse graph --entity "DARPA" --depth 2 returns no nodes or edges, even though correlations exist.
Likely causeHistorical correlations were recorded before graph persistence was enabled (Packet 12), or after a database restore without running graph backfill.
How to checklighthouse correlations --limit 10 — if this returns correlations but graph returns nothing, backfill is needed.
Safe fixRun graph backfill (always dry-run first):
lighthouse graph-backfill --dry-run --limit 100
lighthouse graph-backfill --limit 100

No callsign observations

Symptomlighthouse callsigns returns nothing.
Likely causeEither no live runs have completed yet, the runs were dry-runs (callsigns are not persisted during dry-run), or the callsign_observations table has not been initialized.
How to checkConfirm at least one non-dry-run has completed. Check the DB: sqlite3 data/state.db "SELECT COUNT(*) FROM callsign_observations;"
Safe fixRun a non-dry-run: lighthouse --module adsb --since-days 1. Callsigns are persisted on non-dry-run ADSB and flight runs.

Nostr not publishing

SymptomNo Nostr events published despite correlations existing.
Likely causeOne of the four publishing gate conditions is not met: NOSTR_PUBLISH_CORRELATIONS is not true, no correlation scored ≥ 7.0, or no correlation had ≥ 2 unique signals.
How to checkCheck the log for "skipping nostr publish" lines. Review correlation scores: lighthouse correlations --limit 10.
Safe fixZero publish events is normal when no correlation passes the gate. Do not lower thresholds to force publication. Ensure NOSTR_PRIVATE_KEY_HEX, NOSTR_RELAYS, and NOSTR_PUBLISH_CORRELATIONS=true are set if you expect publishing.

Narrative analyzer skipped

SymptomNo narrative alerts. Log says "narrative module skipped."
Likely causeANTHROPIC_API_KEY is not set.
How to checkecho $ANTHROPIC_API_KEY
Safe fixSet ANTHROPIC_API_KEY in your .env file. The narrative module is optional — the pipeline runs fine without it.

Archive collection fails or returns few pages

SymptomVery few archived pages, or archive module errors in logs.
Likely causeDoD redirected from defense.gov to war.gov (archiver follows redirects, but the URL may need updating in config). DoE has no verified RSS feed — HTML selector fallback may break when the newsroom changes layout. IPFS daemon unavailable (pages save locally, not pinned).
How to checkCheck logs for specific URL failures. Test connectivity: curl -L https://www.defense.gov/News/News-Releases/
Safe fixWithout IPFS, pages still save to data/archives/ — this is acceptable for early production. For the DoD redirect: update ArchiveConfig.targets in config.py to the confirmed canonical URL once known.

IPFS unavailable

SymptomArchive module logs IPFS errors. Pages saved locally but not pinned.
Likely causeIPFS daemon is not running, or IPFS_API_URL is wrong.
How to checkcurl http://127.0.0.1:5001/api/v0/version
Safe fixThis is non-blocking. Pages are saved locally to data/archives/. Start the IPFS daemon if you need pinning: ipfs daemon &. Or use a pinning service (IPFS_PINNING_SERVICE=pinata with PINATA_JWT).

arXiv rate limits (429)

SymptomarXiv sentinel logs HTTP 429 errors. No researcher alerts.
Likely causearXiv rate limiting. The arXiv API has conservative rate limits for automated clients.
How to checkLook for "429" in logs for the arxiv_sentinel module.
Safe fixThis is non-blocking — the module logs the rate limit and exits cleanly. Other modules continue. Run arXiv less frequently (daily rather than every 6 hours) if rate limits are persistent.

SEC entity matching misses a company

SymptomYou expect SEC alerts for a company but see none, even though they have recent 8-K filings on EDGAR.
Likely causeThe company's CIK in data/entities.json is wrong or stale. EDGAR CIK-to-company mappings occasionally change.
How to checkpython scripts/validate_entities.py data/entities.json
Safe fixVerify the CIK at https://www.sec.gov/cgi-bin/browse-edgar?company=&CIK=<CIK>&action=getcompany. Update data/entities.json with the correct CIK. Re-run validation.

podman exec commands fail on Start9

Symptompodman exec lighthouse.embassy lighthouse status fails with "variable not set" or wrong paths.
Likely causepodman exec does not inherit the entrypoint's exported env vars. Environment must be passed explicitly.
How to checkRun with explicit env: podman exec lighthouse.embassy env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db lighthouse status
Safe fixInclude env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db in every podman exec command on Start9 (matches the entrypoint contract; DB_PATH also derives in-app when unset, but podman exec does not inherit the entrypoint env). See Start9 Deployment for full examples.
