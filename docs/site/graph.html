Graph Intelligence

How Lighthouse builds and queries a structured graph of entities, events, and signals over time.

What the Graph Is For

The graph is the primary intelligence interface. Instead of scanning a flat list of alerts, you can ask structured questions: "what signals have touched Lockheed Martin?" or "which entities are two hops from DARPA in the correlation graph?"

The graph grows over time. The longer Lighthouse runs, the richer the traversal becomes.

Graph-native operating model Lighthouse is a graph-native intelligence platform. Correlations, entities, facilities, callsigns, and prefixes are all queryable graph structure — not just log entries.

Graph Nodes

Each node represents one real-world thing. Node types:

Node typeExample IDWhat it represents
entityentity:Lockheed MartinA watched organization
facilityfacility:DARPA HQA physical location in the flight/ADSB config
callsigncallsign:PAT16A tracked aircraft callsign (graph-native since Packet 25)
prefixprefix:PATA callsign prefix — military-style or standard
eventevent:<hash>A correlation event (multi-signal observation)
signalsignal:secA signal type that contributed to an event

Node IDs are deterministic — the same entity always gets the same ID across runs, enabling idempotent upserts.

Graph Edges

Edges connect nodes and encode what the relationship is:

From → ToRelationshipMeaning
entity → event(subject)This entity is the subject of this correlation event
signal → event(contributed)This signal type contributed to this event
event → entity(involves)This event involves this entity
callsign → eventparticipated_inThis callsign was observed during this correlation event
callsign → signalobserved_viaThis callsign was detected by this signal type (ADSB/flight)
callsign → facilityobserved_nearThis callsign was observed near this facility
callsign → prefixhas_prefixThis callsign carries this military-style prefix

Querying the Graph

CLI

# Explore an entity's graph neighborhood
lighthouse graph --entity "Lockheed Martin" --depth 2
lighthouse graph --entity "DARPA" --depth 2 --json
lighthouse graph --entity "MIT Lincoln Laboratory" --depth 2 --json

Depth 2 means: show the entity, its immediate connected events/signals, and any entities one hop beyond those. Depth 3 goes one further hop. The MCP server caps depth at 3.

MCP Tools

For AI agent consumption, these read-only tools are available:

Graph Explanation Engine

The explanation engine (modules/graph_explainer.py) converts raw graph results into human-readable text without using an LLM. It maps signal labels to phrases and generates a plain-language summary of what the graph shows.

Example output: "Lockheed Martin has been connected to 3 correlation events in the last 30 days, involving ADSB military aviation signals and SEC material filings."

Explanation is deterministic — the same graph always produces the same explanation.

Graph Backfill

Graph persistence was added in Packet 12. Correlations recorded before that are stored in correlation_events but have no corresponding graph nodes or edges. The graph backfill command repairs this.

Important: always dry-run first Backfill is idempotent (safe to re-run), but the first real run will make graph-visible any false positives from old correlation records. Review correlation quality before running on a production database with long history. 
# Step 1: Inspect what would be backfilled (no writes)
lighthouse graph-backfill --dry-run --limit 100

# Step 2: Run live
lighthouse graph-backfill --limit 100

# Step 3: Repeat with higher --limit until correlations_seen is less than limit
lighthouse graph-backfill --limit 500

Each correlation adds roughly 2–4 nodes and 3–6 edges. Repeated runs produce zero new nodes/edges (idempotent).

On Start9 (via podman exec)

podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse graph-backfill --dry-run --limit 100

podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse graph-backfill --limit 100

Callsign Intelligence

Callsigns are first-class graph nodes (Packet 25). They are enriched with normalized callsign, prefix, category, and military-style classification, and linked into the graph alongside entities, facilities, and correlation events.

Auto-resolution lighthouse graph --entity PAT16 automatically resolves to callsign:PAT16. You do not need to know the node type prefix — the CLI resolves it. 
# Graph query — resolves PAT16 to callsign:PAT16 automatically
lighthouse graph --entity PAT16 --depth 2 --json

# Observation history (flat list of sightings, separate from graph)
lighthouse callsigns --limit 20
lighthouse callsigns --callsign PAT16 --json

Live callsigns observed near DARPA HQ and Camp Lejeune: MUSL, PAT16, ZEUS31, OTIS61, ELVIS51. Each becomes a graph node on its first correlation, with temporal metadata (first seen, last seen, facility distribution) stored in node properties.

Temporal Intelligence

The real intelligence value is not isolated events — it is sequences and timing relationships. Lighthouse has operational temporal analysis across two modules:

ModuleCLIWhat it provides
modules/temporal_analysis.pylighthouse temporalCallsign recurrence metrics, recent-activity windows, facility aggregation
modules/tempo_analysis.pylighthouse tempoOperational tempo: interval stats, weekday/hour distributions, recurring callsign identification
 
# Recent activity (last 7 days)
lighthouse temporal --recent 7

# Callsign-specific temporal history
lighthouse temporal --callsign PAT16 --json

# Recurring callsigns with mission-pattern signatures
lighthouse tempo --recurring

# Callsign tempo: interval stats and weekday/hour distribution
lighthouse tempo --callsign PAT16 --json
