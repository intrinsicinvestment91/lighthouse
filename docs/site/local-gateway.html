Local Gateway

A private, local-only intelligence dispatch layer that makes Lighthouse data accessible to local tools and agents — without exposing anything publicly.

Private by design All /local/* routes enforce 127.0.0.1 or ::1 access only. Requests from any other address are rejected at the middleware level, before any query runs.

What the Gateway Is

The local intelligence gateway is a bounded, read-only HTTP dispatch layer built into the Lighthouse portal. It provides five structured intelligence methods over a simple JSON API — callable from local scripts, agents, or orchestration tools running on the same machine.

It does not replace the CLI or MCP server. It provides a different access pattern: structured request/response over HTTP, without requiring a persistent MCP connection or shell access.

What It Is Not

  • Not a public API — no auth token, no rate limiting beyond local enforcement; never expose to external networks
  • Not autonomous control — read-only; cannot trigger pipeline runs, write to the DB, or publish to Nostr
  • Not a SaaS endpoint — private, self-hosted, local-first
  • Not an LLM interface — deterministic, bounded queries; no generative output

Starting the Portal

The gateway is part of the portal. Start it with:

pip install -e ".[portal]"
uvicorn portal.app:app --host 127.0.0.1 --port 8080
Bind to 127.0.0.1, not 0.0.0.0 Binding to 0.0.0.0 on a networked machine exposes the portal to your local network. The /local/* routes still enforce IP, but other portal routes (DMS, alerts) would be exposed. Use 127.0.0.1 unless you understand the exposure.

On Start9, the portal is always bound to the container-local address. The /local/* routes are accessible from within the container or via podman exec.

Intelligence Methods

All methods are dispatched via POST /local/request. Each is bounded: MAX_DEPTH=3, MAX_LIMIT=50. Raw alert evidence is stripped from all responses.

callsign.summary

Returns enrichment metadata and operational tempo for a specific callsign. Combines observation history with recurrence patterns.

curl -s -X POST http://127.0.0.1:8080/local/request \
  -H "Content-Type: application/json" \
  -d '{"method": "callsign.summary", "params": {"callsign": "PAT16"}}'

Returns: observation count, first/last seen, facility distribution, tempo metrics, enrichment (prefix, category, military classification).

facility.summary

Returns recent aviation activity and recurring callsigns at a named facility.

curl -s -X POST http://127.0.0.1:8080/local/request \
  -H "Content-Type: application/json" \
  -d '{"method": "facility.summary", "params": {"facility": "DARPA HQ"}}'

Returns: recent callsigns observed, activity counts by day, top recurring callsigns, facility observation window.

correlations.recent

Returns the most recent scored correlation events. Evidence payloads are stripped — only metadata and scores are returned.

curl -s -X POST http://127.0.0.1:8080/local/request \
  -H "Content-Type: application/json" \
  -d '{"method": "correlations.recent", "params": {"limit": 10}}'

Returns: entity, event_type, score, signals, summary, timestamp. Never raw alert payloads.

graph.summary

Returns the graph subgraph around a named entity — nodes and edges up to the configured depth.

curl -s -X POST http://127.0.0.1:8080/local/request \
  -H "Content-Type: application/json" \
  -d '{"method": "graph.summary", "params": {"entity": "DARPA", "depth": 2}}'

Supports the same auto-resolution as the CLI: "entity": "PAT16" resolves to callsign:PAT16. Depth is capped at MAX_DEPTH=3.

intelligence.daily_brief

Returns a cross-domain summary: recent correlations, active callsigns, and a graph snapshot. Designed for daily review or agent ingestion.

curl -s -X POST http://127.0.0.1:8080/local/request \
  -H "Content-Type: application/json" \
  -d '{"method": "intelligence.daily_brief", "params": {}}'

Returns: top recent correlations (evidence stripped), most-observed callsigns in the last 7 days, summary graph statistics. No raw evidence, no personal data.

On Start9

The portal runs as a service inside the Lighthouse container. From within the container (via podman exec), the gateway is accessible at http://127.0.0.1:8080/local/....

# Health check from inside the container
podman exec lighthouse.embassy \
  curl -s http://127.0.0.1:8080/local/health

# Daily brief from inside the container
podman exec lighthouse.embassy \
  curl -s -X POST http://127.0.0.1:8080/local/request \
  -H "Content-Type: application/json" \
  -d '{"method": "intelligence.daily_brief", "params": {}}'

The gateway does not need additional configuration — it reads from the same DB_PATH (explicit or derived from LIGHTHOUSE_DATA_DIR) and LIGHTHOUSE_DATA_DIR as the rest of the pipeline.

Agent and Orchestration Use

The gateway is designed for local agents (BitAgent, shell scripts, or any tool that can make HTTP requests) to query Lighthouse intelligence without shell access. The stable JSON schema means results are easy to parse and forward.

A typical orchestration pattern:

  1. Agent calls intelligence.daily_brief to get a cross-domain summary
  2. Agent filters for high-score correlations or interesting callsigns
  3. Agent calls callsign.summary or graph.summary to drill into specifics
  4. Agent formats and presents the findings — Lighthouse has already done the correlation work
Module source Gateway logic lives in modules/local_gateway.py. The FastAPI routes are in portal/app.py under the /local prefix. The Pydantic request model is GatewayRequest in portal/models.py.
