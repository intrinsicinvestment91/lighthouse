Intelligence Profiles

The foundation for turning Lighthouse into a customizable intelligence application — selectable, declarative mission profiles. Narrow initial activation shipped for repository_capability_discovery v2; active-to-active switching is not implemented.

Status Packet LHP-PROFILE-01 shipped the profile contract, a read-only registry, and backup-readiness inspection. Narrow backup-gated initial activation of repository_capability_discovery v2 is shipped (lighthouse profile-activate, lighthouse active-profile). Not shipped: active-to-active switching, deactivation, migration, rollback, runtime policy resolution, the invention-discovery engine, or a live Gateway bridge. Switch design: ADR-0024.

What an Intelligence Profile Is

An Intelligence Profile is a versioned, declarative policy bundle describing which mission a Lighthouse deployment is configured for — the public scientific mission, private invention discovery, aerospace/defense monitoring, and so on. It declares what is allowed (source categories, collectors, observation tiers, graph/correlation/temporal participation, privacy and publishing policy, backup requirements, interface and dead-man's-switch eligibility) — never how to execute anything.

Profiles own the interpretation; the substrate stays neutral (ADR-0020). The shared platform provides observation, normalization, facts, provenance, temporal history, and the candidate/hypothesis/finding mechanics. A profile owns its detector families and pattern rules, its evidence and counterevidence requirements, and its privacy, publishing and retention policy. This is the first thing a profile would ever be read for at runtime — and it is exactly why a runtime policy resolver (CORE-RESOLVE-01) is a prerequisite before active-to-active switching (ADR-0024). Narrow initial activation is shipped; switching is not.

A profile is not a plugin. It may never declare arbitrary executable modules or shell commands; the validator rejects executable-intent keys anywhere in any policy block. Profiles are safe, reviewable configuration — not code.

Fail-Closed Invariants

  • profile_id is a stable, machine-safe identifier; display_name non-empty.
  • Unknown or future schema_version is rejected.
  • Status is draft, experimental, or ready_for_validation — never "production" or "active."
  • No executable-intent keys anywhere in any policy block.
  • A private profile (local_only) may not enable public publishing.
  • Dead-man's-switch eligibility is declarative only and defaults disabled — eligibility never implies enrollment.
  • A declared backup data_root must resolve under the Start9 /data boundary.

Exactly One Active Profile

At most one profile may govern new intake and derivation at any time. Switching is a controlled, audited state transition — a fenced, compare-and-set active-to-active cutover that never passes through no_active_profile — not an in-place edit. Rollback is bounded (see ADR-0024 §11) — not guaranteed automatic reversibility.

Shipped vs not shipped Shipped: narrow initial activation (no_active_profile → repository_capability_discovery v2) via lighthouse profile-activate. Not shipped: active-to-active switching, deactivation, migration, rollback automation, runtime policy resolution, Gateway-authorized widening switches. Indeterminate projection dimensions refuse unconditionally. Local switch authority requires explicit code/release-owned locally_activatable enrollment — not a seed field (currently empty) and a complete authority projection — no bundled profile is locally switchable today.

Backup Readiness

Before any future profile switch, Lighthouse must prove — read-only — that all authoritative state resolves under /data and can be inventoried. The inspector returns READY, NOT_READY, or UNKNOWN, fail-closed.

Eligibility is not a completed backup A READY verdict means authoritative state is boundary-eligible for backup. It does not assert that a backup has been performed — that is a separate step.

Read-Only Commands

lighthouse profiles                       # list bundled profiles
lighthouse profiles --show <profile_id>    # show one
lighthouse profiles --validate            # validate all bundled profiles
lighthouse profiles --json                # machine-readable

lighthouse backup-readiness               # inspect backup readiness (read-only)
lighthouse backup-readiness --json

These never activate a profile, mutate configuration, write approval state, move data, or trigger a backup.
