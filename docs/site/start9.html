Start9 Deployment

How Lighthouse runs on a Start9 home server — persistent data, backup strategy, and operational commands.

Data warning — read before updating StartOS performs a volume reset on uninstall by default. Uninstalling Lighthouse will wipe /data including all historical intelligence. Always use the Update path (not uninstall + reinstall) to preserve data. Create a backup before any package change.

How It Works

Lighthouse runs inside a container on StartOS with a persistent volume mounted at /data. All intelligence data — the SQLite database, callsign history, correlation records, graph nodes — lives in this volume.

VariableValue on Start9What it controls
LIGHTHOUSE_DATA_DIR/dataAll module output paths (alerts, ADSB, flights, etc.)
DB_PATH/data/state.dbSQLite database path (derives from LIGHTHOUSE_DATA_DIR when unset; set explicitly for podman exec)

The entrypoint script seeds /data/targets.json and /data/entities.json from the image defaults on first run. On subsequent runs, if those files already exist, they are not overwritten — your customizations are preserved.

Seed Files

FileSeeded fromBehavior
/data/targets.json/app/seed/targets.jsonSeeded on first run; operator-customizable afterward
/data/entities.json/app/seed/entities.jsonSeeded on first run; operator-customizable afterward
/app/seed/researchers.jsonBuilt into imageLoaded directly by config; not copied to /data/

Health Endpoint

The MCP server exposes a liveness probe:

GET /health
# Returns: {"status": "ok", "service": "lighthouse-mcp"}

This is used by StartOS to verify the service is running.

Backup Strategy

StartOS has built-in backup support. Use it:

  1. Open the StartOS web UI
  2. Navigate to Lighthouse → Actions → Create Backup
  3. This snapshots the full /data volume

The backup covers everything in /data:

PathContents
/data/state.dbFull SQLite DB — all 13 tables, all intelligence history
/data/targets.jsonOperator target profiles
/data/entities.jsonOperator entity seed
/data/logs/Rotating run logs (last 14 kept)
/data/archives/Archived HTML pages and manifest JSONs
/data/patents/, /data/flights/, etc.Module output JSONs
state.db is your intelligence history Losing state.db means losing all historical alerts, correlations, graph nodes, and callsign observations. Keep regular backups. Back up before every package update.

Safe Update Procedure

  1. Create a backup — StartOS UI → Lighthouse → Backup — before anything else
  2. Use Update, not uninstall + reinstall — the Update path preserves the /data volume
  3. If you must reinstall, restore your backup immediately after install, before starting the service
  4. After any update, run the operational continuity verification (see below)

Restore Procedure

Via StartOS UI: Lighthouse → Actions → Restore Backup.

After restoring, run graph backfill to ensure graph tables are consistent with correlation history:

podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse graph-backfill --dry-run --limit 100

podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse graph-backfill --limit 100

Running Commands on Start9

Use podman exec to run CLI commands inside the container. Always pass the environment variables explicitly — podman exec does not inherit the container's exported env vars.

# Health check
podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse status

# Recent callsigns
podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse callsigns --limit 10

# Recent correlations
podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse correlations --limit 10

# Graph query
podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse graph --entity "DARPA" --depth 2

# Target routing plan
podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse targets --show-routes

Operational Continuity Verification

Run these after any package update, DB restore, or container restart:

podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse status

podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse callsigns --limit 10

podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse correlations --limit 10

podman exec lighthouse.embassy \
  env LIGHTHOUSE_DATA_DIR=/data DB_PATH=/data/state.db \
  lighthouse targets --show-routes

Scheduled Operation

Lighthouse is configured to run on a schedule via the StartOS cron mechanism. The default schedule is every 6 hours.

For a lighter-weight split schedule, you can run modules separately — SEC and correlations every 6 hours, ADSB/flight every 6 hours, arXiv and patents once daily. See Future Plan §7 for the recommended split.

Operational Warnings

  • Do not expose MCP publicly. The MCP server is designed for private/local use. There is no authentication on read-only tools.
  • Do not lower the correlation score gate (7.0) or the 2-signal minimum to increase Nostr output volume.
  • Periodically re-validate entities.json against EDGAR — entity-to-CIK mappings can drift.
  • DoD archive target: defense.gov redirects to war.gov. The archiver follows the redirect, but update the config once a canonical feed URL is confirmed.
