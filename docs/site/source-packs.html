Repository Source Packs

A way for Lighthouse to observe public code repositories as one deterministic observation source — not a second intelligence engine. Canonical source: docs/REPOSITORY_SOURCE_PACKS.md (decision: ADR-0008).

Architecture-only. There is no source-pack ingestion engine in this repository today. The capability is represented by the declarative repository_capability_discovery profile seed and the Gateway's admission flow. This page fixes the architecture so future work doesn't drift.

What it is — and is not

  • A source pack is one observation source that enters the fact-first pipeline: admission → repository intake → versioned observations → normalization → fact store → exact queries and cross-scope facts → profile-owned candidate rules → hypotheses → reviewed findings → optional Gateway-controlled release.
  • It is not a second engine — it never re-derives correlation or graph independently.
  • It is not a plugin and not executable — like profiles, it declares what to observe, never how to execute anything.
  • It is not the invention engine — that is a separate concern, now preserved privately with a provenance manifest, pending selective migration (ADR-0005, ADR-0020).
Corrected (2026-07-14). This page previously said a source pack feeds "observation → alert → correlation → graph → temporal". That path was rejected by the implementation. AlertRecord is a triage contract (score, score label, a minimum-score filter, a publish gate) and a graph edge requires a weight — neither can carry a fact without also asserting an opinion about it, so a source pack routed through them would arrive already judged. Source packs enter the fact substrate. The alert/correlation/graph path remains the legacy OSINT pipeline, untouched and unrelated. See ADR-0008 (superseded in part) and ADR-0020.
Reference-only rule. External repositories named by a capability-discovery profile are never executed, never installed, never imported. Lighthouse reads about a repository to produce observations; it does not run foreign code.

Gateway vs Lighthouse responsibility

ResponsibilityOwner
Source-pack admission approval + auditGateway
Observation produced from an admitted packLighthouse
Fact derivation (normalization, identity, cross-scope)Lighthouse (the one engine)
Interpretation (candidates → hypotheses → findings)Lighthouse, via profile-owned rules (ADR-0020)
Consequential approval / external release / disclosure packagesGateway

Where it fits

Part of Phase D — Repository Intelligence in the roadmap. External packs remain blocked on Gateway source-pack admission and the live bridge (Gateway Boundary); local operator sources are a different class, need no admission, and already ship as lighthouse observe (ADR-0019). When external ingestion is built it must reuse the fact-substrate contracts — the observation model, the normalizer, and the three fact-only tables — and must not be routed through AlertRecord/graph edges.
