Fault Isolation

Each collector module in main.py runs inside its own try/except. A bad WIPO response, a hung Playwright session, or a 429 rate limit will log the traceback and set that module's result to an empty list. It will not abort subsequent modules or the Nostr broadcast.

This means: if arXiv times out, SEC still runs. If the archive crawler fails, ADSB still runs.

Configuration Layer

config.py holds 13 typed dataclass singletons for all module settings. Access is via getter functions, never by importing the singleton directly in module code.

All data output paths in config are resolved via _data_path(rel), which delegates to modules/data_paths.py — the canonical reader of LIGHTHOUSE_DATA_DIR and DB_PATH (defaults to "data"; "/data" on Start9). Never hardcode "data/..." path strings.

Alert Layer

Every signal output uses AlertRecord from modules/alerts.py as the canonical contract. An alert always includes: source, alert_type, score, score_label, provenance, payload, schema_version.

Alerts are persisted via db.insert_alert(). No module bypasses this — hand-crafted alert dicts that skip AlertRecord.validate() are rejected.

Score dimensions: source reliability, keyword strength, recency, uniqueness, watchlist match. Composite 0–1 score maps to high / medium / low labels.

Correlation Engine (A3)

The correlator (modules/correlator.py) runs four detectors across accumulated alerts:

  • Temporal — multiple alerts within a time window
  • Spatial — alerts mentioning the same facility or region
  • Entity — alerts referencing the same named entity
  • Cross-source — alerts from different signal types (e.g. ADSB + SEC)

Scoring uses modules/correlation_scoring.py — deterministic weighted scoring that accounts for signal mix (ADSB military + SEC materiality outranks flight + narrative), multi-signal bonuses, and evidence quality. Scores range 1–10.

A deception filter marks single-source events as probationary. Single-source events have is_single_source=True and lower trust.

Every persisted correlation stores a deterministic SHA-256 witness hash of its canonical claim (modules/witness.py). In the production path (correlator._attach_witness_survival) no signing key is passed, so the witness signature field is stored empty. A BIP-340 signing helper exists for demonstration and tests only (modules/_schnorr.py, not for production keys); signed witness attestations are a future intention. Optional Nostr publishing signs Nostr events separately with coincurve.

Graph Layer

On every successful correlation, modules/graph_builder.py converts the CorrelationRecord into nodes and edges, which are upserted to graph_nodes and graph_edges via modules/db.py.

Node types: entity:<name>, event:<hash>, facility:<name>, signal:<type>.

Edge types encode relationships: entity → event contributions, signal → event contributions.

Graph traversal is BFS, depth-limited (max depth 3 via MCP tools). All graph reads are via modules/db.py traversal helpers.

Callsign Layer

modules/callsigns.py provides deterministic callsign normalization and enrichment. ADSB and flight alerts include callsign_enrichment metadata: normalized callsign, prefix, category, military-style flag.

Callsign observations are persisted to callsign_observations (a separate table, not the main graph). This enables repeated callsign analysis — the same callsign at the same facility on multiple runs becomes stronger evidence.

Graph-native callsigns (promoting recurring callsigns to graph nodes) are planned for a future packet.

MCP Interface

The Lighthouse MCP server (portal/mcp_server.py) exposes 14 tools across 5 phases. All read-only tools are bounded (limit ≤ 100, depth ≤ 3) and DB-safe. Write/publish tools require an approval_token and default to dry_run=True.

Nostr Publishing Gate

All four conditions must be true before a correlation publishes to Nostr:

  • NOSTR_PUBLISH_CORRELATIONS=true
  • not dry_run
  • correlation score >= 7.0
  • at least 2 unique signals

Only five fields may appear in a published note: entity, event_type, score, signals, summary. Raw alert payloads are never published.

Database

Alert, correlation, graph, and callsign persistence goes through modules/db.py. Its SQLite file derives as $LIGHTHOUSE_DATA_DIR/state.db unless DB_PATH explicitly overrides it. Per-module deduplication caches in state_db.py use AppConfig.state_db_path and DmsConfig.db_path, which always resolve to $LIGHTHOUSE_DATA_DIR/state.db and do not follow a differing DB_PATH. An explicit DB_PATH can intentionally separate those stores.

Key tables: alerts, correlation_events, graph_nodes, graph_edges, callsign_observations, plus 9 tables in state_db.py for per-module caches (patents, flights, SEC filings, DMS, etc.).

Schema migrations are handled via _ensure_alerts_column — new columns are added live and are safe against existing databases.

Start9 Deployment Model

On Start9, Lighthouse runs in a container with LIGHTHOUSE_DATA_DIR=/data and DB_PATH=/data/state.db (recommended explicitly for podman exec; the application derives DB_PATH from LIGHTHOUSE_DATA_DIR when unset). The entrypoint seeds targets.json and entities.json from the image to /data/ on first run. Researchers are loaded directly from /app/seed/researchers.json by config — they are not copied to /data/.

See Start9 Deployment for the full operations guide.
