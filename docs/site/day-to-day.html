Day-to-Day Usage

How an operator actually uses Lighthouse — from health checks to graph queries to production runs.

Check System Health

Always start here. This confirms the database, schema, keys, and recent activity are all in order.

lighthouse status

Review Your Targets

See which target profiles are loaded and what signals each one activates. This is read-only and safe to run any time.

lighthouse targets
lighthouse targets --show-routes
lighthouse targets --json

The --show-routes flag shows which signals (SEC, ADSB, flight, arXiv, etc.) each target activates and what entities/keywords/regions are in scope.

Review Recent Alerts

Alerts are raw or semi-processed signals from individual collectors. They may include noise. Use them for debugging and to understand what each module is seeing.

# Last 20 alerts
lighthouse alerts --limit 20

# Filter by source
lighthouse alerts --source sec_sentinel
lighthouse alerts --source adsb_sentinel

# Filter by score
lighthouse alerts --min-score 0.75

# Filter by entity
lighthouse alerts --entity "Lockheed Martin"

# Machine-readable output
lighthouse alerts --limit 20 --json

Alert labels: high, medium, low. High-label alerts are most worth reviewing.

Review Correlations

Correlations are more important than raw alerts. They represent multiple independent signals pointing at the same entity within a time window. This is the primary output surface.

lighthouse correlations --limit 10
lighthouse correlations --limit 10 --json
Correlations, not alerts, are the signal A single alert is noise. A correlation with score ≥ 7.0 backed by 2+ independent signals is meaningful and may be published to Nostr.

Check Callsign History

Callsign observations are stored persistently. Use these to review aviation activity over time.

lighthouse callsigns
lighthouse callsigns --limit 20
lighthouse callsigns --callsign PAT16
lighthouse callsigns --callsign PAT16 --json

Callsigns like PAT16, ZEUS31, MUSL, OTIS61 have been observed near DARPA HQ and Camp Lejeune. A callsign seen at the same facility on multiple separate runs is more significant than a one-time observation.

Temporal Activity

Query historical patterns across callsigns and facilities. These commands read from the callsign_observations table without affecting scores or the graph.

# Activity across all callsigns/facilities over the last 7 days
lighthouse temporal --recent 7
lighthouse temporal --recent 30 --json

# Callsign-specific temporal history
lighthouse temporal --callsign PAT16
lighthouse temporal --callsign PAT16 --json

# Facility activity summary
lighthouse temporal --facility "DARPA HQ"

Use this to answer: "How active has this callsign been in the last month?" or "Which facilities have had the most activity this week?"

Operational Tempo

Operational tempo analysis identifies recurring mission patterns — callsigns that appear repeatedly, on consistent days/times, at the same facilities. All deterministic, no ML.

# Find callsigns with recurring mission patterns
lighthouse tempo --recurring
lighthouse tempo --recurring --min-observations 5 --min-days 3

# Callsign-specific tempo (interval stats, weekday/hour distribution)
lighthouse tempo --callsign PAT16
lighthouse tempo --callsign PAT16 --json

# Facility operational cadence
lighthouse tempo --facility "DARPA HQ"

A callsign that appears every Tuesday and Thursday between 0800–1200 near the same facility is a qualitatively different signal than a one-time observation.

Investigate an Entity

Graph traversal is the primary intelligence interface. Start with a known entity and explore what signals have touched it.

lighthouse graph --entity "Lockheed Martin" --depth 2
lighthouse graph --entity "DARPA" --depth 2 --json
lighthouse graph --entity "MIT Lincoln Laboratory" --depth 2 --json

Depth 2 means: show the entity, its immediate events/signals, and entities one hop beyond those. Higher depth values produce richer (and larger) output.

The graph grows as correlations accumulate. If queries return sparse results, run graph backfill.

Graph Backfill

Historical correlations may not have corresponding graph nodes if they were recorded before graph persistence was enabled (Packet 12). Backfill is idempotent — safe to run multiple times.

# Always dry-run first
lighthouse graph-backfill --dry-run --limit 100

# Then run live
lighthouse graph-backfill --limit 100

# Repeat with higher limit until count_seen is less than limit
lighthouse graph-backfill --limit 500

Run in Targeted Mode

Targeted mode reads data/targets.json, builds a routing plan, and runs only the signals enabled in your active target profiles. This is more efficient than running all modules and produces less noise.

lighthouse --module targeted --dry-run --since-days 7
lighthouse --module targeted --since-days 7

Standard Production Run

The recommended production workflow:

# Step 1: Validate entities
python scripts/validate_entities.py data/entities.json

# Step 2: Run tests (without publishing credentials)
env -u NOSTR_PRIVATE_KEY_HEX -u NOSTR_PUBLISH_CORRELATIONS pytest tests/unit -v --tb=short

# Step 3: Dry-run first
lighthouse --module all --dry-run --since-days 7

# Step 4: Take a backup
mkdir -p backups
cp data/state.db backups/state-before-run-$(date +%Y%m%d-%H%M%S).db

# Step 5: Live run with log capture
mkdir -p logs
lighthouse --module all --since-days 7 > logs/live-$(date +%Y%m%d-%H%M%S).log 2>&1

Or use the production wrapper:

scripts/run_lighthouse_prod.sh

Reading Logs

tail -200 logs/live-*.log

Look for:

  • Module failures — each module runs in its own try/except, so one failure does not abort the rest
  • Rate limits — arXiv may return 429; this is non-blocking
  • Correlation count — how many events were scored this run
  • Nostr relay acceptance — whether published events were accepted
  • Zero publish events — normal when no correlation passes the 7.0 gate

Rollback

If a run produces unexpected results, roll back the database:

cp backups/<backup-file>.db data/state.db

Also disable publishing before investigating:

NOSTR_PUBLISH_CORRELATIONS=false lighthouse status

Running Individual Modules

For debugging or lightweight runs, target a single module:

lighthouse --module sec --since-days 7
lighthouse --module adsb --since-days 1
lighthouse --module flight --since-days 1
lighthouse --module arxiv --since-days 14

Available module choices: patents | velocity | arxiv | sec | archive | narrative | flight | adsb | nostr | targeted | all

Note on patent module The patent provider is disabled by default. Running --module patents or --module all will skip patent collection without error. See Signal Sources for details.

Observe Your Own Repositories and Documents

Everything above watches the outside world. This watches your work — local git repositories and documents — and records what it finds as plain facts. Nothing here is scored, ranked, or interpreted.

Two declarations are required, and they are not interchangeable. LIGHTHOUSE_OBSERVATION_ROOTS is the trust boundary: it is empty by default, and empty means observe refuses rather than quietly trusting your whole filesystem. data/observation_sources.json is the work list — it can only narrow the roots, never widen them.

export LIGHTHOUSE_OBSERVATION_ROOTS=/home/you/Projects   # the trust boundary

# data/observation_sources.json — the work list (there is no default, and no seed file)
# {"schema_version": 1, "sources": [
#   {"type": "repository", "path": "/home/you/Projects/widget"},
#   {"type": "document",   "path": "/home/you/Documents/spec.pdf"}
# ]}

lighthouse observe --dry-run    # observes and normalizes; writes NOTHING, not even the tables
lighthouse observe              # persist (insert-only, idempotent by content identity)

Observing never modifies the source. The repository tree — .git/ included — is byte-identical afterwards, and that is a tested property rather than a promise.

Inspect What Was Recorded

Read-only, and enforced as such by SQLite itself: these queries run on a mode=ro connection, so the store cannot be written through them even by mistake. An empty store answers {"count": 0}, exits 0, and creates no database.

lighthouse observations list                 # every recorded observation, newest first
lighthouse observations show --id 9f3c1ab2   # full digest, or an unambiguous >=8-char prefix
lighthouse observations search --scope-type repository
lighthouse observations search --sensor git_metadata     # filesystem | git_metadata | text_extractor
lighthouse observations stats                # counts only, ordered by name — never by count

--sensor is the real provenance: the sensor that established a fact, read verbatim from the stored artifact. A repository is the subject of an observation, not a sensor — so there is no --source flag.

Ask Where Else

The question the fact store was built to answer: where else have I built this? Both commands perform exact lookup and direct set intersection over facts that are already stored. Neither ranks, infers, scores, or interprets anything.

# Every scope in which one exact entity was directly observed
lighthouse observations where --entity-id technology:docker
lighthouse observations where --entity-id language:Python --json

# The exact entities observed in EVERY requested scope (intersection, never union)
lighthouse observations shared --scope-id <A> --scope-id <B>
lighthouse observations shared --scope-id <A> --scope-id <B> --scope-id <C> --json

# "Which of my projects contain these EXACT bytes?"  (no new command — a new entity type)
lighthouse observations where --entity-id content:<sha256-of-the-raw-bytes>

Entity ids are exact — technology:docker, language:Python, remote:<url> are not digests, so they have no prefix form. Scope ids are digests, so they accept an unambiguous prefix of at least 8 hex characters (observations list prints them). An unknown entity is an empty result and exit 0; an unknown scope is an error — reporting an empty intersection would claim "these two share nothing" about a repository that was never observed.

Two repositories with a Dockerfile do not share the file — they share the technology, and (if the bytes match exactly) the content A file: id embeds the scope it was found in, so file:<A>:Dockerfile and file:<B>:Dockerfile are different entities by construction — that has not changed. What they join on is technology:docker, and, since LHP-INTEL-03A, content:<sha256> whenever the two files are byte-for-byte identical. By the same design, repository: and document: ids cross scopes too: a document is identified by the digest of its bytes, so the same file saved in two places is one entity observed twice.

Exact File Content

content:<sha256> is SHA-256 over a file's exact raw bytes, and nothing else — not the path, not the name, not the mode, not the timestamps, not decoded text, not normalized line endings, and not git's blob SHA-1 (which hashes a header before the bytes, so it could never match a loose file's digest). A rename keeps the identity; one changed byte replaces it. Because a standalone document is identified by its bytes too, a repository file and a document holding the same bytes are one entity with two occurrences.

Only tracked files are read. Untracked and ignored files are never opened, symlinks are never followed, submodules are never recursed into, and a file that changes while it is being read produces no digest at all. Every tracked path still gets an accounted outcome — hashed, missing, unreadable, too_large, aggregate_limit_exceeded, symlink_unsupported, gitlink_unsupported, special_file_rejected, changed_during_read, invalid_path — and only hashed may carry a digest.

Identical bytes mean identical bytes. Nothing else. Two of your projects containing the same Dockerfile is a fact. It does not say the file was copied, which copy came first, who wrote it, whether two implementations were independent, or that any of it matters. Before treating a content inventory as complete evidence, check content.coverage.complete: above 5,000 tracked files the inventory is withheld entirely rather than truncated, because a truncated list reads exactly like a complete one.

Review Pattern Candidates

The first surface that shows you something other than a raw fact. It runs one deterministic rule that a profile declared in advance — the same exact bytes appear in at least two distinct repository scopes — and lets you record one local decision about what it found. It does not score, rank, promote, publish, execute, or activate a profile.

lighthouse patterns detect --dry-run --json   # writes NOTHING — not a row, not a table, not the DB file
lighthouse patterns detect                   # persist (insert-only, idempotent by content identity)
lighthouse patterns list                     # latest version per candidate, with its decision if any
lighthouse patterns list --all-versions --json
lighthouse patterns show --id 9f3c1ab2       # full pc_<sha256>, or an unambiguous >=8-char hex prefix
lighthouse patterns review --id 9f3c1ab2 --operator-id operator \
    --decision needs_more_evidence --reason "Repository lineage has not been assessed."

Three decisions, and the vocabulary is closed: accepted_for_followup ("worth more investigation" — never "true"), dismissed, needs_more_evidence. There is deliberately no approved, verified, finding or published. One decision per candidate version, bound to the exact evidence digest; when the evidence changes the detector produces a new version to review, and your earlier decision is never touched.

A candidate is not a finding. It says "these direct facts satisfy one declared review rule; look at this" — and it has no field in which it could say more. It does not say the files were copied, that one project derived from another, that anything was independently invented, reusable, novel, patentable, or important. For a solo operator reusing their own boilerplate, the dominant explanation for identical bytes is a clone, a fork, a template, a generated file or a vendored copy — the detector cannot tell those apart, so it says so on every candidate. source_independence_not_assessed is mandatory. Reviewing a candidate is a private note to yourself: it creates no finding, contacts no Gateway, publishes nothing, and authorizes nothing.

Check Public Sources

Record whether Lighthouse could fetch an admitted public locator, when, and what directly happened — an append-only history through one hardened HTTPS chokepoint. Set the allowlist first (empty refuses); the targets file may only narrow it.

export LIGHTHOUSE_PUBLIC_SOURCE_HOSTS=archive.example.org,data.example.edu   # empty => refuses
lighthouse public-sources check --targets-file data/public_source_targets.json --dry-run   # writes NOTHING
lighthouse public-sources check --targets-file data/public_source_targets.json             # persist (append-only)
lighthouse public-sources runs
lighthouse public-sources history --content-digest <sha256>
lighthouse public-sources show --id psc_<sha256>

A not_found is HTTP 404/410, never a claim that a source is gone; a timeout or TLS failure is not an absence. The exact-byte digest (content:<sha256>) joins to repository and document content identity, but the response body is never stored. No candidate is created (ADR-0022).

Local Gateway

When the portal is running, the local intelligence gateway provides structured JSON access to intelligence data for scripts and local agents — no shell access required.

# Health check
curl http://127.0.0.1:8080/local/health

# Daily intelligence brief (correlations + callsigns + graph snapshot)
curl -s -X POST http://127.0.0.1:8080/local/request \
  -H "Content-Type: application/json" \
  -d '{"method": "intelligence.daily_brief", "params": {}}'

See Local Gateway for all five methods and Start9 usage.
